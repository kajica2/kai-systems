02 — Architecture

Four layers. Each one does one thing.

The twin is not a single agent. It's a layered system — scan, model, reason, orchestrate — where each layer feeds the next and none of them require a human in the loop once the work is defined.

1
Scanner
Index the environment
Runs on demand or on a cron. Traverses the filesystem at startup — reads package.json, requirements.txt, agent skills, installed tools (brew, pip, npm), GitHub repos, Obsidian vault index. Outputs a structured snapshot of every tool, project, and capability available right now. If a new package appears, the scanner finds it on the next run.
2
Model
Persist the inventory as memory
The scan output writes to a durable layer — memory/user.md for cross-project preferences, memory/agent.md for agent behavior, and a project-level twin index for domain-specific context. This is what allows the twin to know "I already have a transcription pipeline" without re-running discovery. The model is the memory of the environment.
3
Reasoner
Match work to tools
Given a job — "transcribe this recording", "build a landing page for X", "run the weekly report" — the reasoner reads the model and selects the right tools in the right order. It's not an LLM doing freeform reasoning from scratch; it's a routing decision constrained by the actual inventory. If Whisper and pYIN are installed, route audio transcription there. If not, route to the API. The reasoner picks from what's actually available.
4
Orchestrator
Set up and run the work process
Once the reasoner picks the path, the orchestrator sets up the process — writes a subagent prompt, schedules a cron, triggers a webhook, or hands off to the next agent in the chain. The orchestrator also handles failure modes: if a step fails, it retries, rolls back, or escalates to the human digest with a diff. The orchestrator is the part that does the work. The other three layers exist so it always knows what it's working with.
03 — Running Processes

What the twin has already set up.

The twin doesn't just describe the environment — it acts on it. These are the processes it has already built or maintains.

ArXiv + GitHub research swarm — cron-triggered subagent that runs every 48 hours. Polls arXiv for new AMT (automatic music transcription) papers, checks GitHub for tool updates, writes a summary. Result lands in music-transcription-monitor/docs/ and triggers a GitHub Pages rebuild.
↓
Puppeteer deploy-test loop — fires on every web deploy. Visits the live URL, asserts HTTP 200, checks DOM for expected strings, fails on console errors, re-deploys and retries if the check fails. This is the twin verifying its own output.
↓
Memory maintenance — after each session, the twin appends durable learnings to memory/user.md (cross-project rules), memory/agent.md (agent behavior), or project-level AGENTS.md (repo-specific context). The next agent that spins up reads the model and starts with working context.
↓
E2E regression gate — after any sprint (multi-step code change), the twin runs the project's end-to-end test before reporting done. Typecheck + build pass don't count. The test must pass. If it fails, the sprint isn't done.
The twin is not a dashboard. A dashboard shows you what's happening. The twin acts on what it finds. If a cron job fails three times in a row, the twin doesn't tell you — it flags it, rolls back the broken deploy, and puts the diagnostic in your next digest. You read the report, not the process.
04 — Twin Instances

Domain-specific twins built from the scan.

The general scanner produces domain-specific instantiations. Each twin knows its domain cold and runs the process without asking.

Music Twin

Index: Ableton projects, Pro Tools sessions, MuseScore scores, sample libraries, Max for Live patches, Vital presets. Knows the full instrument and FX chain. Routes requests to the right environment — Suno for demos, DAW for production, Solokit for analysis.

Trumpet Twin

Index: live recordings, transcription output, charts, practice logs. Scans the trumpet stack directories. Keeps the pYIN + VexFlow pipeline warm. Routes new recordings to the ingest → transcribe → chart flow automatically.

Web Twin

Index: all kajica2.github.io pages, Vercel deploys, GitHub Pages repos. Keeps all spokes linked to the hub. Monitors every deploy with the Puppeteer gate. Notifies (or auto-reverts) on failure.

Research Twin

Index: arXiv, GitHub trending, bob_mover_jazz_lexicon, Solokit corpus, Obsidian vault. Runs the AMT research swarm. Keeps the music-transcription-monitor dashboard current. Alerts when a new relevant paper or tool appears.
